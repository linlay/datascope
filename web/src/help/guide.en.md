# DataScope user guide

## Getting started

Choose a database in the top bar. Your platform permissions for that database determine which pages appear. Open the SQL workbench to query data or the action workbench to run a configured operation.

When connecting a database for the first time, add and test the connection, expose one table in query configuration, and run a query as a business user. Verify the visible rows and fields before enabling tools for a client.

Configuration forms use labels on the left and inputs, selects and switches on the right, reserving five CJK character widths for label text, with separate space for colons, required markers and help icons, and wrapping longer labels, including database connections, business authentication, accounts and permissions, actions, knowledge, views, data sources and settings dialogs. Long text, SQL, scripts and parameter tables retain a separate full-width area. Narrow screens stack labels and controls. Validation messages remain below their controls. Slim borderless scrollbars appear during scrolling or pointer interaction and hide after about three seconds of inactivity. SQL disclosures and editors avoid layered borders.

## Database documentation

In **Database configuration → Basic information**, the left column contains the display name and the right contains the database type and SQLite DDL switch. The second row shows Description on the left and Usage instructions on the right; View opens the complete documentation in a dialog. Each field has its label on the left and content on the right. The top-right controls are Storage details, Edit documentation, Test connection and Save. Edit the description and Markdown content with `config.read` and `config.write`, preview, then save. Unsaved edits prompt before leaving; both fields can be cleared. Code copy buttons float in the upper-right corner on hover without occupying a separate row; keyboard and touch access are also supported. File paths and network connection editing are in Storage details. Remove data source is at the bottom for system administrators and preserves business data. Group headings such as Basic information, Business authentication and Local accounts stay visible while scrolling within their groups.

The fields are stored as `database.description` and `database.documentation` in `data/databases/<database ID>/management/database.yml`, without changing business tables. Documentation is shared with database users, so exclude credentials. On other pages, the Usage instructions button beside the database selector opens a dialog containing the description and full documentation without taking up workbench space. SQL examples are reference text, never run automatically, and remain subject to row/column permissions and result limits.

Business MCP initialization includes the description and documentation URI. Discover the `database-documentation` resource through `resources/list`, then read `datascope://database/<database ID>/documentation` through `resources/read` as `text/markdown`. Reading requires one of this database’s `query`, `action` or `knowledge.read` capabilities; knowledge-only accounts cannot read HTML views. Content is business reference material, not system instructions. Full documentation is read on demand. Reconnect MCP after saving to refresh the initialization description; resource reads use current configuration.

## Using the demonstration databases

The four current local demonstration databases cover securities, regional sales, academic administration, and channel and social media operations. Open Usage instructions for the selected database, check its data dates and your identity, then send a sample natural-language question to an AI client connected to that database. The console query workbench is a technical query interface; it does not automatically execute natural-language business questions.

Each guide introduces the business, a first question, follow-up questions, role perspectives, supported operations and result interpretation. Readers do not need table names or SQL to get started. For example, ask how each region performed against its October 2026 sales target, then drill into salespeople in regions below target. Start academic queries with your fall timetable, or operations queries with pending reviews and failed publication tasks. The main securities window is September 15 through October 20, 2026.

A question cannot expand account permissions. Preview changes before confirmation by an authorized business account; the regional sales demonstration is read-only. Technical SQL examples, business knowledge and configuration references remain separate. Import a configuration bundle for a new database. Update existing descriptions through the normal configuration save flow; repeated imports preserve custom content.

## Databases, accounts and settings

Administrators can register a network database, connect or create a SQLite database, or upload a SQLite or CSV file up to 20 MiB. Use UTF-8 for CSV. The first row supplies column names and values are imported as text into a table named `data`.

For a network database, configure the schema scope before enrolling tables. Use **Add database** in the top bar and choose **New configuration** to fill in settings, or **Clone an existing database** to select a source and enter a new name and connection. Source connection fields are prefilled for editing; enter the password again and supply the target path for SQLite. File uploads can also supply the new database. Cloning creates a separate database, then previews and confirms selected tables and columns, query policies, Actions, knowledge and views. Authentication is optional and unchecked by default. Network targets first enroll the source’s configured tables and must have a compatible schema. The source remains unchanged. Business data, passwords, accounts and grants are not copied; MCP and writes start disabled. Retry failures on the same new database, or choose **Keep database and configure later**, without creating a duplicate.

System administrators can open Database configuration → Basic information → Storage details → Edit connection to maintain a network database's host, port, read-only account, password and TLS. Leave the password blank to keep it; new passwords are encrypted. Use Test connection to check the draft, then Validate and save. Saving repeats the connection test and checks that enrolled columns still exist with compatible types, nullability and primary-key attributes. Failure preserves the previous configuration and password. Existing action write connections receive the same host, port and TLS settings, keep their separate account and password, and are also tested. Refresh and retry if another window has saved changes. Successful edits retain the source ID, permissions and business configuration and create an audit entry. This entry is for maintenance of the same business database; matching structure cannot prove that business data is identical. Create a new source to switch business databases or database types. SQLite has no editing entry, and database names and schema scope are not changed in this dialog.

Platform accounts sign in to the console. Database grants control access to configuration and workbenches. Business identities determine data visibility and authorization for real actions. Configure business authentication and capabilities for the selected database. For OneID connection guidance, use the help button beside Authentication service, or Authentication provider when using a global provider. Open system settings in the top bar to change language or appearance and access authorized platform settings.

## Query configuration, SQL workbench and table data

Query, action, knowledge and view configuration fill the available workspace. Lists and editor content scroll independently within their panels, keeping panel headings and controls visible. The query configuration table list is capped at 420px to accommodate schema-qualified names while giving remaining wide-screen space to details.

Select a table in query configuration, expose the required fields, set row filters and limits, and configure masking for sensitive fields. The row filter section is always visible: its heading is Row-level filtering when SQL is empty and Row filter SQL when populated. Expand it to add SQL directly; entering SQL automatically selects Filter with SQL, while clearing it selects No row filter. Query precondition SQL lets you set a condition that must pass before a query and a rejection message; leave it empty to skip this check. Both SQL sections are collapsed by default, whether empty or populated. A SQL configured or No SQL configured tag beside each heading indicates whether it contains SQL. Select a heading to expand or collapse its editor; collapsing does not change policy enforcement or saving. Save the policy. Test with one record the business user should see and one they should not see.

In the SQL workbench, choose an identity and run a read-only SELECT. For a database with a customers table, try `SELECT customer_no FROM customers WHERE customer_no = :number` with parameters `{"number":"C001"}`. Inspect the rewritten SQL and results. Users with full query access can compare the raw results.

Use the table data page to browse and filter stored records with full query access. To check a business user's visibility, use that identity in the SQL workbench.

## Data sources, import scripts and schedules

Choose the target database and open Data sources. Search, create and select tasks in the Import list on the left; edit scripts, schedules and parameters in Import details on the right. Use the External connections button beside the list title to add, edit, test connections or browse schema in a dialog. You can also add a connection directly from task details. Opening the connection dialog preserves unsaved task drafts. Connections can serve multiple tasks, and a task can read multiple connections. SQLite sources connect only to existing files. Referenced connections cannot be deleted. Passwords are encrypted; leave the password blank when editing to keep it.

On the Script tab, implement synchronous `function main(params, context)`. Read with `sources.get("alias").query(sql, [values])` and access the current target with `db.target().query/update(sql, [values])`, using `?` placeholders. JS controls transformation, joins, pagination and insert/update rules. Target tables must already exist. Network targets require an enabled independent writer in Action configuration; SQLite imports use a separate writer independently of the Action switch.

Save, use Rollback trial to inspect logs and affected rows, then Run now. A trial executes the entire saved script and rolls back without advancing the checkpoint. A real run uses one target transaction and commits only on success; errors, timeouts and stops roll it back. Use `context.log(message)`, `context.checkpoint` and `context.saveCheckpoint({...})` for logs and progress. The checkpoint is saved after target commit; interruption between them can cause replay, so scripts must tolerate duplicates. Each query permits up to 1,000 rows and fails on overflow; paginate large tables in JS. Scripts have no async, network, filesystem or npm support.

Schedule supports manual, one-time, fixed interval and daily runs. Check the timezone and estimated times, save and enable automatic execution. The same task cannot overlap; missed schedules coalesce into one execution and failures do not retry automatically. The default timeout is 300 seconds, configurable from 1 to 3,600 seconds. Scheduling runs in admin-api and continues when the browser closes.

Open the separate Data run history menu before SQL workbench to view status, logs, script version, actual parameters and progress, and filter by import task. The Data run history button in the task editor opens that task’s records. Stop a running task from its details. Affected rows from trials, failures and stops do not indicate committed data. Check business data before rerunning interrupted or unknown outcomes. Access requires `config.read` and `source.write`. This explicitly permits reading sources and writing the target outside business query row/column policies and masking, so grant it separately.

## Action configuration and script reference

New actions default to `main(params, context)`. Obtain the current database connection with `db.session()`, read with `conn.query` / `conn.queryOne`, and write with `conn.update`, using literal SQL and `:name` parameters. Queries do not automatically apply normal query permissions: scripts must check record ownership using `context.userId` and verify `result.rowsAffected` after writes. Export shared functions with `exports.fn` and load them with `require("./library")`. The following reference describes the compatible `run(args, ctx)` template; do not mix the two script APIs.

Create an action with a name, description and typed parameters. Implement the synchronous entry point `function run(args, ctx)`. Declare id as an integer and value as a string for the example below. Configure a write connection and enable writes before testing the action.

| Interface | Behavior |
| --- | --- |
| `my.one` | Applies query policies and returns the first visible row or null. |
| `my.all` | Applies the same policies and row limits and returns an array. |
| `db.one` / `db.all` | Read trusted data outside query policies. Return the first row or null, or an array, respectively. |
| `db.exec` | Runs one INSERT, UPDATE or DELETE and returns the affected row count. |
| `deny(message)` | Rejects the action, rolls back the transaction and returns the reason. |
| `ctx.userId` / `ctx.now` | The business identity and the fixed UTC time for this operation. |

Use backticks for SQL. Values inside `${...}` are bound parameters. Write table and column names directly in the template. This example assumes records has id, owner_id and value columns. The update checks ownership when writing.

```js
function run(args, ctx) {
  const row = my.one`SELECT id FROM records WHERE id = ${args.id}`;
  if (!row) deny("Record missing or inaccessible");
  const count = db.exec`UPDATE records SET value = ${args.value}
    WHERE id = ${args.id} AND owner_id = ${ctx.userId}`;
  if (count !== 1) deny("Record changed or update denied");
  return { id: args.id, updated: count };
}
```

To share logic, create a library in the same database, export a function with `export function`, and use `import { fn } from "library"` in the action.

**AI assistance** requires `config.read` and `action.write` on the database. Set `DATASCOPE_AI_ENDPOINT`, `DATASCOPE_AI_MODEL` and the provider's `DATASCOPE_AI_KEY` on admin-api and restart it. Use a gateway base ending in `/v1` or the full `/v1/chat/completions` endpoint. For a provider HTTP 404, check the endpoint and model name. For `AI service returned an invalid response`, inspect the detailed reason: `finish_reason=length` means truncated output; increase the provider output token limit or shorten the request. JSON or field-type errors require checking model JSON-object support. Complete JSON code fences and streams explicitly finished with `stop` but missing `[DONE]` are supported; incomplete output is rejected. The server reads model output incrementally and displays the validated proposal when complete. If parameter or script validation fails, the assistant attempts one correction using the diagnostic when the context size permits. The correction must pass all validation checks. Action SQL uses the shared parser subset, so `ILIKE` is unsupported even for PostgreSQL. For case-insensitive pattern matching, use `LOWER(name) LIKE LOWER(${args.pattern})` with a bound pattern value; verify collation and Unicode case behavior on the target database. If a proposal fails parameter or script validation, the error includes the specific cause (such as a parameter type, module syntax, library import or SQL template error). Add that cause to your request and regenerate, or edit the draft manually; rejected proposals are not applied. The default idle wait for the first or next output is 120 seconds. Administrators can adjust it with `DATASCOPE_AI_TIMEOUT`. If the error still reports 30s, check for an explicit old deployment value, set `DATASCOPE_AI_TIMEOUT=120s`, and restart admin-api; recreate containers when their environment changes. The reverse proxy must allow for the complete generation and a possible correction attempt. The bundled Docker management proxy waits up to 600 seconds; configure any outer gateway accordingly. Open **AI assistance** at the top right of the action editor to start a conversation in the right drawer. Try “Update items.name by id only when owner_id equals the current business identity.” The assistant uses the current draft, dialect, enabled table columns and library functions. Continue with follow-up conditions or clarification answers; each request includes the last six successful turns. The drawer shows request status, duration, a model-provided thinking summary and the response. The summary is a public explanation of the approach, not private reasoning. The request record explicitly states that the assistant does not call model tools or execute action SQL. You can stop generation while waiting. Compare the proposal with the draft, select parameters and script independently, then click **Apply to draft** and confirm. Review and save. Editing the draft or changing context invalidates old proposals. Conversation history stays in page memory. Manual editing remains available when the model is offline.

## Testing and executing actions

1. Fetch the action list in the action workbench. Select an action and inspect its parameter schema and confirmation requirements.
2. Enter JSON parameters and a business identity for a dry run. Inspect the return value and planned writes. Dry runs always roll back. Use a new request when testing changed input.
3. For a real call, publish the action, enable its MCP tools and grant the business account action capability. Authenticate with your own business identity on the real-call tab. If confirmation is required, open the returned link, review the preview and confirm.
4. If a call is interrupted, query the result with the same request_id. For an unknown outcome, check the audit log and business records before retrying.

In the rollback tab, editors who also have `impersonate` can select **Generate test arguments**, review and adopt the test case, then edit the arguments and expected result. Choose a business identity and run the trial yourself. For the same id, compare the write plan, affected rows and denial reason for the manager and a different user. **Explain trial** sends only parameter types, a diagnostic category or the return type and affected row counts. For an identified script defect, select **Take repair to draft** to generate and review an edit. Changing the editing context discards stale proposals.

## Knowledge configuration and workbench

Create entries for business terms, metric definitions or query examples in knowledge configuration. Choose a searchable name, save the content and check publication status. In the knowledge workbench, list entries, search for a business term and inspect the matching document's preview and JSON. Check the database, publication status and account capabilities if an entry is missing.

## View configuration and workbench

In View configuration, Preview HTML opens a separate dialog with scrolling confined to the preview frame; closing it returns to the original editor position. Create an HTML view from a template, enter its identifier, name and HTML, and save the draft. In the view workbench, preview with sample data, then use an identity preview to verify visible records, fields and empty results. After publication, load it in the real business preview with your own business identity. Actions invoked there can perform real writes. To recommend the view for queries, select MCP display recommendation in View configuration and choose it in the dialog. This is optional: clients decide whether to use it, and it does not change query data or the SQL workbench. If only the identity preview is empty, run the underlying query with the same database and identity and check the field names.

## Connecting an MCP client

The platform management connector uses `/mcp/admin`, separately from each database's business MCP. Management MCP supports SQLite DDL object inspection, preview, execution and history when DDL management is enabled and permissions allow it. Preview to obtain a plan_id before applying; check execution records when the result is uncertain. Business MCP does not expose DDL. System administrators can also test and save candidate network connections or remove a data source registration. Removal preserves business files; connection editing cannot change the target database.

The action AI assistant follows the current draft entry point: main uses db.session() and CommonJS; legacy run retains tagged SQL templates without automatic migration. Both contracts reject new or changed policy-bypassing SELECT statements relative to the saved action. Author and review any new reads manually.

Enable the required tools in MCP configuration and save. Actions, knowledge and views each have a master switch in their list heading and on MCP configuration. Both locations update the same state immediately; the sidebar shows Enable / Enabled. Save any draft before toggling. Action listing, parameter descriptions and execution toggle together; first-time network activation requires an independent write account. Knowledge search and reading toggle together. The views switch controls published HTML discovery and reading; disabling it removes default display recommendations while SQL queries continue. Publication status is preserved. Business access still requires global MCP enablement and account capabilities. Actions require `action.write`; knowledge requires `knowledge.write` or `mcp.write`; views require `view.write` or `mcp.write`. Query tools remain individually selectable, and MCP address/tool changes use Save. Configure the client using the displayed connection information and the database's business authentication method. For OAuth, select `mcp` in the client and follow the authorization redirect. Use the database account provider for local business accounts or an enterprise SSO provider for enterprise sign-in. The Discovery URL link at the top right of Database configuration → Business authentication opens the active OAuth resource metadata; hover to view the full URL. Unsaved authentication changes do not affect this link. List the tools before sending a test request.

For clients that support connector packages, enable MCP, save and download the connector ZIP. Import it in the client and authenticate for the selected database.

For queries, enable and call `list_tables`, `describe_table` and `query` in order. For actions, use `list_actions`, `describe_action` and `invoke_action`. If a tool or resource is missing, check tool settings, publication status and the account's capabilities for the selected database.

## Maintaining local example data

Run these commands from the repository root. They operate only on the specified local example database and preserve authentication, business accounts and permission configuration. Avoid concurrent business writes during maintenance.

For securities, run `python3 examples/securities/compact.py --db data/securities_demo.sqlite3 --keep-days 20`. It backs up the full database to `data/backups/`, then retains the latest 20 trading days of positions and daily balances, keeping all ledgers by default. For further reduction, run `python3 examples/securities/compact.py --db data/securities_demo.sqlite3 --keep-days 20 --trim-ledgers --preserve-account 880000001186`. This also trims older orders, trades and cash flows while preserving the specified account's full ledgers for Action regression. The local result is approximately 47.32 MiB (49.62 MB), covering September 15 through October 20, 2026. All customers, accounts, scopes, quotes and original indexes remain; retained records and opening balances are not recalculated. Repeat `--preserve-account` for additional accounts; it requires `--trim-ledgers`. Use `--backup-dir` to select the backup directory. `--keep-days` must be positive and follows the latest stored snapshot, not the computer date. Ledger trimming validates foreign keys and 15 ledger invariants before committing, rolling back on failure. If space reclamation fails after commit, restore from the backup. Regression accounts retain extra history, so turnover totals and rankings must use the same explicit date window; SQL examples now specify it. Consult the backup for older complete history; missing records do not mean zero. Use the full backup for historical statistics or load tests. Stop services accessing the database before restoring it.

`make init-shop` creates a shop with 200 customers, 100 products and 3,000 orders spanning May through October 2026. To expand an existing minimal example, run `python3 examples/shop/generate.py --db data/shop_demo.sqlite3 --expand-existing`. It backs up the database before filling in missing data and preserves existing rows. Default creation refuses to overwrite existing files.

The shop covers four order statuses, customers without orders, products without sales and zero stock. Sales revenue is `quantity*unit_price_cents` for paid and shipped orders, in integer cents. SHOP001 sees only business identity 1's customers and orders. Everyone can read the product catalog, with costs hidden. `examples/shop/sql-examples.yml` provides monthly sales, customer and product rankings, status distribution and empty-data queries. Import them through the configuration bundle for a new database; copy them into the query workbench to run them against an existing database. Repeated imports preserve custom configuration.

Run `make init-academic` to create `data/academic_demo.sqlite3`, approximately 14 MiB, containing 1,000 students, 80 teachers and two semesters of timetables, enrollments, grades, attendance and exams. To connect it to the platform, set `DATASCOPE_EXAMPLE_PASSWORD` (at least 12 characters), then run `make check-example EXAMPLE=academic` and `make import-example EXAMPLE=academic`. The five example accounts are ACA001 (registrar), ACA002 (school administrator), T1001 (teacher), F2001 (counselor) and 202301001 (student). Repeated imports preserve existing databases and accounts.

Select the academic database and a business identity in the query workbench, then use the SQL examples to check visible timetables, grades and attendance. Students see only their own released grades; teachers see their assigned sections; counselor scopes follow appointment dates. Pending scores are NULL, not zero. Pass rates include only courses with all three assessments released. Enrollment counts describe records visible to the current identity; enrollment actions independently check actual capacity. Dry-run enrollment, withdrawal, grading, publication or room changes in the action workbench before confirmation by the corresponding business account. The default snapshot is November 13, 2026, after the add/drop deadline, so enrollment and withdrawal must be denied. Only assigned teachers can grade, only the lead teacher can publish, and released grades are locked. Successful add/drop regression cases use a September 10, 2026 snapshot and trusted execution time on that date. Names, contacts and the academic calendar are fictional; see `examples/academic/guide.md` for definitions.

Run `make init-channel-operations` to create `data/channel_operations_demo.sqlite3`, approximately 22 MiB, with four simulated platforms, 12 accounts, 600 content topics and 1,600 publication tasks. Set `DATASCOPE_EXAMPLE_PASSWORD`, then run `make check-example EXAMPLE=channel-operations` and `make import-example EXAMPLE=channel-operations`. OPS001–OPS007 represent an administrator, lead, analyst, editor, operator, external collaborator and another team's lead. Services do not install examples automatically; repeated imports preserve existing configuration and accounts.

Use the query workbench to check account grants, content assignments and ten SQL examples. Cross-platform views are not deduplicated reach. Never sum cumulative snapshots or follower balances across days; missing metrics are NULL, not zero. Keep unavailable organic/paid splits unknown. Platform-reported conversions and first-party seven-day last-click attribution are separate, and unknown attribution stays unassigned. Only administrators, leads and analysts can read promotion costs; external collaborators see assigned content. Dry-run submission, review, scheduling, simulated publication results, comment handling or editor assignment in the action workbench before confirmation by the corresponding business account. Content visibility does not grant account operation rights, READ grants cannot write, and future tasks cannot be marked successful early. Publications and replies only change local fictional records. See `examples/channel-operations/guide.md` for definitions.

## Audit logs and troubleshooting

Select a database or platform logs on the audit page. Narrow the results by request ID, operator, business identity or tool. For a failed call, check its database, identity, tool, policy version and outcome.

- **Missing menu item** — Check the selected database and platform account grants.
- **Unexpected empty query** — Verify the parameters, business identity and row filters in the rewritten SQL.
- **No change after a dry run** — Dry runs roll back. Check the real call and its confirmation status in the action workbench.
