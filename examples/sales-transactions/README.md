# 销售交易与仓储履约关联演示

两个小型 SQLite 上游共同为现有区域销售库提供业务数据。销售交易来源约 76 KiB，仓储履约来源约 68 KiB；默认只有 **5 个客户、6 件商品、20 张订单、40 条订单明细、2 个仓库**。全部为虚构数据，金额为人民币整数分。

交易库负责订单与回款退款；[仓储履约库](../warehouse-fulfillment/README.md)负责发货、退货收货和库存快照。两者使用相同的订单及明细编号，抽取后直接进入区域销售库已有业务表，不使用孤立的 `imported_*` 接入表。

## 创建和接入

先准备已登记的区域销售库及现有平台管理员。没有区域销售库时，按其 README 创建并导入配置；以下命令不会重建它。

```sh
make init-supply-chain-demo
# 设置 DATASCOPE_EXAMPLE_PASSWORD（至少 12 字符）后：
make check-example EXAMPLE=sales-transactions
make check-example EXAMPLE=warehouse-fulfillment
make import-example EXAMPLE=sales-transactions
make import-example EXAMPLE=warehouse-fulfillment
make check-supply-chain-demo
make import-supply-chain-demo
```

生成器只读区域销售库，选取其中 5 个客户、6 件商品及 2 个仓库作为映射资料，创建两个来源和抽取清单到 Git 忽略的 `data/supply-chain/`。**客户、商品、组织和仓库沿用目标库已有主数据，本例不演示主数据新增或修改同步。** 自定义目标路径、来源目录或目标数据库 ID 时，使用 `generate.py --target <文件> --directory <目录> --database-id <ID>`；相应配置包数据库路径及通用导入器的 `-file` 也需调整。SQLite 文件必须位于平台允许目录。

已有来源或清单一律拒绝覆盖。生成器检查目标业务表的 `8100001..8109999` 编号段未被占用；所有新增业务记录只使用该编号段，订单号为 `UP-202611-001..020`。已有客户、商品、账号、权限和历史订单不修改。首次正式导入会增加 20 张订单及相关单据；**区域销售合计随之变化**。

`make import-supply-chain-demo` 先通过 SQLite Backup 备份目标到 `data/supply-chain/target-before-*.sqlite3`，再用通用 `cmd/import-sources` 保存两个外部连接及四条任务，按顺序分别完成回滚试运行和正式运行。备份只含业务库，不包含账号、权限或任务进度；不是整套环境恢复包。每条任务独立提交，整套安装不提供跨任务事务。重复导入保留已有连接、脚本、开关和进度；失败后补齐依赖再重跑即可。

## 四条抽取任务

在区域销售库的「数据来源」查看任务，在「数据运行记录」查看结果。

| 顺序 | 任务 | 目标表 | 预设间隔 |
| --- | --- | --- | --- |
| 1 | 订单与明细 | sales_orders、sales_order_items | 2 分钟 |
| 2 | 发货与退货 | shipments、shipment_items、sales_returns、sales_return_items | 3 分钟 |
| 3 | 回款与退款 | payments、payment_allocations、refunds | 5 分钟 |
| 4 | 库存快照 | inventory_balances | 10 分钟 |

自动运行默认关闭，首次导入完成后可逐任务开启。间隔不代表依赖编排；订单或退货尚未导入时，下游任务整次失败且不推进水位，补齐上游后需手动重跑或等待下一计划。不同来源没有统一读快照，短暂的订单状态与履约明细不同步属于演示中的最终一致性。

每个对象在 `*_changes` 中只有最新 `change_seq`。首次全量与后续增量使用同一脚本；`batchSize` 为 1–20（默认 20），小批量时重复运行直至完成。目标记录按主键插入或更新，相同内容不重复写入；整次失败或回滚试运行不提交目标数据、不推进正式水位。设置临时参数 `{"batchSize":20,"simulateFailure":true}` 可体验写入后失败回滚。

这是固定规模、只支持新增和更新的小例子；取消订单保留记录，**不演示硬删除、CDC、完整事件回放或跨库分布式事务**。每张订单固定两条明细，子单据远少于脚本每次查询的 100 行上限，不应直接用于大规模生产迁移。

## 演示增量变化

先完成初次抽取，再执行一次：

```sh
make advance-supply-chain-demo
make import-supply-chain-demo
```

推进只修改两个来源，随后运行抽取才改变目标。该有限演示只能推进一次；第二次会明确拒绝，不会无限造数。两个来源文件使用一次本地 SQLite 跨文件事务更新。

| 对象 | 初始状态 | 推进并抽取后 |
| --- | --- | --- |
| UP-202611-001 | 部分发货；1 张发货单共 2 件；回款 50% | 已发货；2 张发货单共 4 件；2 笔回款合计 100% |
| UP-202611-002 | 4 件已发货；退货 1 件并退款 | 保持不变，用于核对净销售和应收 |
| UP-202611-019 | 待确认，无发货和回款 | 已取消，记录保留 |
| 库存记录 8100001 | 2026-11-15 快照，在库 41 件 | 同一快照更正为 39 件，不累加为新流水 |

首次共导入 15 张发货单、15 笔回款、1 张已收货退货单、1 笔退款、12 行库存快照；推进后为 16 张发货单及 16 笔回款，订单总数仍为 20。

业务日期为 **2026-11-01 至 2026-11-16**。区域销售原有 SQL 示例固定于 2026 年 10 月，查看新数据需明确指定 11 月，或筛选 `order_no LIKE 'UP-202611-%'`。库存按 `snapshot_date` 选定时点，不能把 10 月和 11 月快照相加；本例未新增 11 月销售目标，不能将缺失目标视为零。

可在已连接来源库的 AI 客户端提问“列出销售交易库的 20 张订单”“订单 001 分几次回款”；在仓储库查看同一订单发货；在区域销售库核对抽取后的结果。不能直接跨三个 MCP 库执行 SQL JOIN。

来源查询账号分别为 **TX001**、**WMS001**，业务身份均为 1，可读各自小库的全部演示记录，无业务写入动作。密码来自配置导入时的环境变量；抽取任务由拥有 `config.read` 和 `source.write` 的平台用户执行，不向来源业务账号授予抽取权限。

## 验证

```sh
go test ./tests/examples -run TestSupplyChainBusinessImports -count=1
```

验收使用隔离数据库，覆盖两个声明式配置包、依赖先到、分页、试运行、失败回滚、无水位重放、增量补发与补款、取消、库存修订及外键完整性，不写本地业务库。
